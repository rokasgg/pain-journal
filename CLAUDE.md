# React Native Boilerplate Guidelines

## Tech Stack
- Framework: Expo (React Native) with Expo Router (File-based navigation)
- Language: TypeScript (Strict mode)
- Styling: NativeWind v4 (Tailwind CSS)
- State Management: Zustand
- Backend/Auth: Supabase (`@supabase/supabase-js`), session persisted via `@react-native-async-storage/async-storage`
- Forms: React Hook Form + Zod (`@hookform/resolvers/zod`)
- Toasts: `Alert.alert` from `react-native` (no third-party toast library — see Toasts section)
- Theming: NativeWind `colorScheme` (from `nativewind`) synced with a persisted Zustand store
- Media: `expo-image-picker` (selection) + `expo-image` (display) + Supabase Storage (upload)

## Coding Rules
1. ALWAYS use TypeScript with strict interfaces. Do not use `any`.
2. ALWAYS use NativeWind `className=""` for styling instead of Inline `style={}` or `StyleSheet.create`.
3. Use Functional Components with Named Exports.
4. Keep navigation inside the `app/` directory using Expo Router standards.
5. Use icons from `@expo/vector-icons`.
6. NEVER use deprecated React Navigation imports.

## Project Structure
```
src/
  app/            # Expo Router routes only (screens + _layout.tsx). No business logic here.
    _layout.tsx   # Root Stack. Owns the auth redirect guard (see Auth Flow below).
    (auth)/       # Unauthenticated group: login, register, forgot-password. Own Stack layout, headerShown: false.
    (tabs)/       # Authenticated group: Tabs layout (Home, Explore, Profile) with @expo/vector-icons.
    modal/        # Modal-presented routes, registered individually in the root Stack (e.g. edit-profile).
  components/
    ui/           # Reusable, presentational primitives (Button, Input, ThemeSwitcher, etc.)
  lib/
    supabase.ts   # Supabase client singleton
    validations/  # Zod schemas, one file per domain: <domain>.ts (e.g. auth.ts, profile.ts)
  store/          # Zustand stores, one file per domain: use<Domain>Store.ts
  utils/
    toast.ts      # Thin wrapper over Burnt (success/error/info)
    image.ts       # expo-image-picker helpers (permission request + launch)
```

## Components (`src/components/`)
- Reusable UI primitives live in `src/components/ui/`, PascalCase filenames matching the exported component (e.g. `Button.tsx` exports `Button`).
- Export via named export, never `export default`, for components in `components/`.
- Accept a `className?: string` prop (and `<field>ClassName?: string` for styled sub-elements, e.g. `textClassName`) so callers can extend/override styling — merge it into the base className string, don't replace it.
- Extend the underlying RN component's props via `interface XProps extends PressableProps { ... }` rather than redefining known props.
- For components with visual variants (e.g. `variant?: 'primary' | 'secondary' | 'outline'`), define a `Record<Variant, { container: string; text: string }>` style map above the component and look up classes from it — don't branch styling inline with ternaries in JSX.
- Route screens (`app/**`) use `export default function ScreenName()` (required by Expo Router); everything else uses named exports.

## NativeWind Styles
- `tailwind.config.js` has `darkMode: 'class'` — always pair a light class with a `dark:` variant for any color-bearing className (backgrounds, text, borders). Never ship a screen/component that only looks correct in one color scheme.
- Standard screen container: `flex-1 items-center justify-center bg-white dark:bg-black` (or `bg-white dark:bg-black px-6` for forms).
- Standard text color pair: `text-black dark:text-white`. Secondary/placeholder text: `text-gray-500`/`#8e8e93` (also used for `placeholderTextColor`, which NativeWind can't style directly).
- Inputs: never hand-roll a `TextInput` on a screen — use `components/ui/Input` (`rounded-lg border border-gray-300 px-4 py-3 text-black dark:border-gray-700 dark:text-white`, switches to `border-red-600 dark:border-red-500` when it has an `error`).
- Primary buttons: `rounded-lg bg-black py-3 dark:bg-white` with inverted text `text-white dark:text-black`; for buttons with multiple variants, use the `components/ui/Button` component instead of hand-rolling one.
- Never use `StyleSheet.create` or inline `style={}` for anything expressible in Tailwind; `style` is reserved for values NativeWind cannot express (e.g. dynamic numeric layout from measurements).

## Session State (`src/hooks/useSession.ts`) + Zustand Stores (`src/store/`)
- **Session/user state does NOT live in a Zustand store.** It lives in the TanStack Query cache under the `['session']` key, owned by the `useSession()` hook — `{ session, user, isLoading }`. `useAuthStore` holds no state at all, only action methods (see below). If you're adding session-derived state, extend `useSession()`/the query cache, not `useAuthStore`.
- `useSession()` subscribes to `supabase.auth.onAuthStateChange` (ref-counted so N callers share one listener) and pushes every event straight into `queryClient.setQueryData(['session'], ...)`; the initial `fetchSession()` query has `staleTime: Infinity` since only that listener is allowed to update it.
- Zustand stores are for domains that either (a) are pure actions with no state (`useAuthStore`), or (b) own genuinely local/persisted state (`useThemeStore`). One file per domain, named `use<Domain>Store.ts`, exporting a single hook `use<Domain>Store`. Type with `create<XState>((set) => ({ ... }))` — no untyped stores.
- `useAuthStore` — action-only, no `interface XState` with data fields, just `AuthActions`: `signUp(email, password, name)`, `signIn(email, password)`, `signOut()`, `resetPassword(email)`, `updateProfile({ name?, avatarUrl? })`, `uploadAvatar(userId, localUri)`. All of it calls `supabase.auth.*` and returns `Promise<{ error: string | null }>` (or `{ url, error }` for `uploadAvatar`) — never throws. Callers check `error` and forward it to `toast.error(...)`; nothing here calls `set()` because there's no state to set — auth-state changes flow to consumers via the `onAuthStateChange` listener inside `useSession()`, not through this store.
- `useThemeStore` is the one store that does own real state directly via `set()`, persisted with zustand's `persist` middleware + `createJSONStorage(() => AsyncStorage)`: `mode: 'system' | 'light' | 'dark'`, `setMode(mode)` (also calls NativeWind's `colorScheme.set(mode)`; `onRehydrateStorage` re-applies it on launch so NativeWind and the persisted preference never drift).
- A dev-only escape hatch, `skipAuthForDev()` in `src/utils/devAuth.ts`, writes a fake session directly into the same `['session']` query cache key so the rest of the app is reachable without a working Supabase backend — wired to a button on the login screen. It bypasses Supabase entirely; any screen that actually calls Supabase (reset password, profile update, sign out) will still fail against a placeholder project even after using it.

## Expo Router Routes (`src/app/`)
- Two top-level route groups: `(auth)` for unauthenticated screens and `(tabs)` for the authenticated app shell. Each group has its own `_layout.tsx` (`Stack` for `(auth)`, `Tabs` for `(tabs)`), both with `headerShown: false`.
- Auth gating lives ONLY in the root `src/app/_layout.tsx`: it reads `session`/`isLoading` from `useSession()`, compares against `useSegments()[0] === '(auth)'`, and calls `router.replace(...)` inside a `useEffect` to redirect. Do not duplicate redirect logic in individual screens.
- `(tabs)/_layout.tsx` defines tab icons via `@expo/vector-icons` (`Ionicons`), colored using `useColorScheme()` — not NativeWind — since `tabBarActiveTintColor`/`tabBarStyle` are native navigator options, not styleable views.
- Link between screens with `<Link href="/(auth)/register" asChild>` wrapping a `Pressable`, not raw `router.push` unless imperative navigation is required (e.g. post-action redirects, which use `router.replace`).
- Adding a new screen = adding a file under the correct group; adding a new tab = adding both the screen file in `(tabs)/` and a `<Tabs.Screen name="..." />` entry in `(tabs)/_layout.tsx`.
- Modal screens live under `src/app/modal/` and are registered individually in the root `_layout.tsx` with `<Stack.Screen name="modal/<name>" options={{ presentation: 'modal', headerShown: true, title: '...' }} />` — the modal group is NOT wrapped in its own `(group)` layout the way `(auth)`/`(tabs)` are, because each modal needs its own `presentation`/`title` rather than sharing one. Open one with `router.push('/modal/<name>')`; close with `router.back()`.

## Supabase (`src/lib/supabase.ts`)
- One client singleton, `supabase`, created with `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY` (read from `.env`, see `.env.example`). If either is missing, it `console.warn`s and falls back to placeholder credentials (`https://placeholder.supabase.co` / `placeholder-key`) instead of throwing — the app must always boot without a `.env` file; only actual auth calls fail, not module init. Never reintroduce a hard `throw` here.
- Session persistence uses a custom `authStorage` wrapper around `@react-native-async-storage/async-storage`, not the raw module — it probes `isAsyncStorageAvailable()` first and falls back to an in-memory `Map`-backed storage (`getItem`/`setItem`/`removeItem`) if the native module is missing or any call throws (e.g. web/Expo Go edge cases). `persistSession: true`, `autoRefreshToken: true`, `detectSessionInUrl: false` since this is native, not web. When the fallback is active, sessions won't survive an app restart — that's expected, not a bug to fix by making AsyncStorage calls unguarded again.
- All Supabase calls go through `useAuthStore` actions or the `useSession()` hook — screens and components never import `supabase` directly.
- `supabase.auth.getSession()` / `supabase.auth.onAuthStateChange()` are only called inside `useSession()` (`src/hooks/useSession.ts`), not directly in `_layout.tsx`. Root `_layout.tsx` shows a full-screen `ActivityIndicator` while `useSession().isLoading` is true, then applies the `(auth)`/`(tabs)` redirect.

## Auth screens
- **Auth inputs declare `textContentType`/`autoComplete`:** register uses `newPassword`/`new-password` on *both* password fields, login uses `password`/`current-password`, plus email/name. Without them iOS guesses, and painted its yellow "Strong Password" autofill styling onto only the repeat-password field, which made it look unstyled.

## Form Validation (React Hook Form + Zod)
- Schemas live in `src/lib/validations/<domain>.ts` (e.g. `auth.ts`), one `z.object({...})` per form, each exporting both the schema and its inferred type: `export type XFormData = z.infer<typeof xSchema>`.
- Cross-field checks (e.g. `confirmPassword` matching `password`) use `.refine()` with an explicit `path: ['field']` so the error attaches to the right input.
- Screens with a form use `useForm<XFormData>({ resolver: zodResolver(xSchema), defaultValues: {...} })` and wrap every input in `<Controller control={control} name="field" render={...} />` — never manage form fields with raw `useState` once a Zod schema exists for that form.
- Render validation errors via the `Input` component's `error={errors.field?.message}` prop; never show them in a toast (toasts are for API/network outcomes, not per-field validation).

## Toasts (`src/utils/toast.ts`)
- Always call `toast.success(...)` / `toast.error(...)` / `toast.info(...)` from `@/utils/toast` — never call `Alert.alert` directly in a screen/component. `Alert.alert` is no longer used anywhere in the app; `ConfirmModal` (see below) replaced every call site, including this one.
- Use toasts for the outcome of an async action (API error message, "Password reset email sent!", etc.), triggered right after `await` resolves in the submit handler. Do not toast validation errors — those render inline under the relevant `Input`.
- Implementation: `toast.*` calls `useToastModalStore.getState().show(message, variant)` (`error` → `'destructive'`, `success` → `'success'`, `info` → `'info'`) — a plain non-persisted Zustand store, since `toast.ts` is called from outside React (Zustand actions, hooks) and can't use a hook directly. `ToastModalHost` (mounted once in root `src/app/_layout.tsx`, inside `ErrorBoundary`, rendered *after* `<Stack>` so paint order puts it on top) subscribes to that store. Still no third-party toast library — a prior version used `burnt`, which requires a native module unavailable in Expo Go and kept crashing on cold start; don't reintroduce a native-toast dependency.
- Note the UX tradeoff versus the old native `Alert.alert`: toasts are now a blocking dialog requiring a tap to dismiss, not an auto-dismissing banner. This was an explicit choice to keep toast styling consistent with the rest of the app's design system.
- **`ToastModalHost` deliberately does NOT use `ConfirmModal`/RN's `<Modal>`** — it renders its own plain absolutely-positioned `View` overlay instead (`className="absolute inset-0 ..."`, returns `null` when not visible). A real native `<Modal>` presenting at the exact moment a navigator-modal screen (`presentation: 'modal'`) is being dismissed raced the dismiss transition and froze touch input (mainly Android). A plain in-tree overlay can't conflict with navigation at the native level since it's never a separate native window. `ConfirmModal` itself is unaffected and still uses `<Modal>` normally — its other call sites (sign-out confirm, delete confirm, `InfoButton`) aren't followed by navigation, so they're not at risk. If a future toast-adjacent component needs the same "shown right after a modal-screen dismiss" pattern, follow `ToastModalHost`'s plain-overlay approach, not `ConfirmModal`'s.
- The `'success'` variant renders a small (48px, outline, `colors.primary`) `AnimatedCheckmark` (see the Success Animation section) above the message text — a fresh instance every time the overlay becomes visible, since the early `if (!visible) return null` unmounts it when hidden. `'info'`/`'destructive'` don't get the checkmark (info isn't a completion, destructive is an error). The confirm/close button is also styled per variant now (`CONFIRM_BUTTON_STYLES`/`CONFIRM_BUTTON_TEXT_STYLES` in `ToastModalHost.tsx`): `'success'` uses a quiet bone-white/outline button (`bg-bone` — new palette token in both `tailwind.config.js` and `theme.ts`, `#F5F0E6`) rather than solid primary, so it doesn't visually compete with the checkmark above it; `'info'` keeps the solid primary button, `'destructive'` keeps solid red.
- **Call order matters for the `'success'` checkmark: every `onSaved` handler calls `toast.success(...)` (or `.error`/`.info`) *before* `router.back()`, never after.** `AnimatedCheckmark`'s draw animation starts immediately in a `useEffect` on mount; firing the toast after `router.back()` lets the outgoing screen's transition animation (see Navigation Transitions below) eat into the checkmark's first frames while the JS/native thread is busy with that transition, so by the time the overlay is actually visible on screen the animation already reads as partway done. Calling the toast first mounts and starts painting the overlay while the current screen is still frontmost and nothing else is animating, *then* `router.back()` plays underneath it. `checkin/[type].tsx` and `flare-up/new.tsx` originally had this backwards (toast after back) — this was the exact bug reported and fixed. Keep new `onSaved` handlers toast-then-back.
- The `'success'` variant also fires `haptics.success()` and `'destructive'` fires `haptics.error()` (see the Haptics section; `'info'` stays silent) in a `useEffect`. **Note the dependency array is `[visible, variant]`, not `[]`** — unlike `AnimatedCheckmark`, `ToastModalHost` itself is mounted once, permanently, from the root layout; only the JSX it returns is conditionally `null` (the early `if (!visible) return null`), so an empty-deps effect placed above that guard would fire exactly once ever, on app start, not once per toast. `[visible, variant]` fires it on every genuine transition into a success toast. Haptics don't reliably work in simulators — verify on a real device.

## Reusable Form Input (`src/components/ui/Input.tsx`)
- Wraps `TextInput` with an optional `label`, `error` (renders red helper text and switches the border to red), and `isPassword` (renders an eye/eye-off `@expo/vector-icons` toggle and manages visibility internally — don't pass `secureTextEntry` yourself when using `isPassword`).
- Forwards its ref (`forwardRef<TextInput, InputProps>`) so it works as a `Controller` render target and with RHF's `ref` wiring.
- Any new form field type (e.g. a future `Select`) should follow the same shape: `label?`, `error?`, `className?`, forwarded ref, RN props spread last.
- `className` applies to the **outer container** (the same root element `label`/`error` render inside), not the inner `TextInput` — this matters for layout props like `flex-1`/`w-full` when placing an `Input` inside a `flex-row` (e.g. next to a remove button in a dynamic list row): passing `className="flex-1"` has to land on the element that's actually the flex child, or it silently does nothing and the field renders at its unstretched intrinsic width.
- A separate `inputClassName` prop (added for the physio visit form's large notes field — see Pain/Neck Tracker Domain) targets the inner `TextInput` itself, for cases where the field's own size/appearance needs overriding independent of the outer container — e.g. `inputClassName="flex-1"` to have a multiline field fill the remaining height of a flex-column step, or a fixed height like `h-48` inside a `ScrollView` (where `flex-1` has no defined parent height to fill).
- **Keyboard handling:**
  - **Multiline `Input`s automatically attach the shared iOS "Done" bar** (`inputAccessoryViewID={KEYBOARD_DONE_BAR_ID}`, from `src/components/ui/KeyboardDoneBar.tsx`). It's a single `InputAccessoryView` mounted **once** in root `_layout.tsx`. Return in a multiline field only inserts a newline, so without the bar there was no way to close the keyboard: the physio-visit notes step was the reported case. The bar renders nothing on Android, which has its own hide-keyboard key. A raw multiline `TextInput` must opt in with the same id.
  - **Form `ScrollView`s use `keyboardShouldPersistTaps="handled"` + `keyboardDismissMode="interactive"` + `automaticallyAdjustKeyboardInsets`**, so tapping outside or swiping down closes the keyboard. A form step must never be a plain `View` with an input in it: `StepVisitNotes` was, and nothing could dismiss the keyboard there.
  - **Full-screen wizards without a native header** (`physio-visit/new.tsx`) wrap their body in `KeyboardAvoidingView` (`behavior="padding"` on iOS, offset 0), so the footer buttons stay above the keyboard.
- **Never use a free-text `Input` with `keyboardType="decimal-pad"` for an hours field.** `decimal-pad` restricts the on-screen keyboard but not a pasted value or a physical/third-party keyboard, so `Number(text)` on garbage input silently produces `NaN`, which then fails `zod`'s `z.number()` validation with a confusing error. All three hour fields (`sleep_hours`, `screen_time_hours`, `exercise_hours` in `MorningFields.tsx`/`EveningFields.tsx`) use `src/components/ui/HoursMinutesPickerField.tsx` instead — no free text is possible.
  - `HoursMinutesPickerField` renders as two side-by-side native `Picker`/`Picker.Item` wheels from `@react-native-picker/picker` (added specifically for this — plain autolinked native module, no config plugin), one for whole hours and one for minutes (`minuteStep`, default 15), shown inline below a `Pressable` trigger with a Cancel/Done row (same layout convention as `DatePickerField`'s iOS spinner block). Value stays a single decimal-hours `number` (e.g. `1.5` = 1h 30m) to match the existing `sleep_hours`/`screen_time_hours`/`exercise_hours` columns and zod schema — the two-column split is presentation-only, converted via `toParts()`/committed as `hours + minutes / 60`. Each field passes its own `maxHours` (14/16/4). An earlier version showed one flat list of decimal options (e.g. "13.5") — replaced because it read poorly and didn't match how people think about durations. Native pickers can't be styled with NativeWind `className`, so dark mode is handled via `itemStyle={{ color: ... }}` reading `useColorScheme()` — the one other sanctioned exception to "no native color branching" alongside the tab bar case in `(tabs)/_layout.tsx`.

## Theming (`src/store/useThemeStore.ts`)
- `tailwind.config.js`'s `darkMode: 'class'` is driven exclusively by NativeWind's `colorScheme.set('system' | 'light' | 'dark')` (imported from `'nativewind'`) — never call `Appearance.setColorScheme` or branch styling off `useColorScheme()` from `react-native` in app code (the tab bar's native-options case in `(tabs)/_layout.tsx` is the one sanctioned exception, since those are non-style navigator props).
- The user-facing control is `components/ui/ThemeSwitcher` (segmented System/Light/Dark), backed by `useThemeStore`. Add new theme entry points by calling `useThemeStore((s) => s.setMode)`, never by importing `colorScheme` directly in a screen.
- The store is the single source of truth and is persisted; don't re-derive or cache the mode elsewhere (e.g. component-local `useState`).

## Media / Avatars (`src/utils/image.ts`, `useAuthStore.uploadAvatar`)
- Picking a photo always goes through `pickAvatarImage()` from `@/utils/image` — it requests media-library permission (toasting an error and returning `null` if denied) and launches `expo-image-picker` with `mediaTypes: ['images']`, `allowsEditing: true`, `aspect: [1, 1]`. Don't call `expo-image-picker` directly from a screen.
- Uploading is a two-step flow, always in this order: `uploadAvatar(userId, localUri)` (uploads to the Supabase Storage `avatars` bucket at `${userId}/avatar.<ext>`, `upsert: true`, returns a cache-busted public URL) then `updateProfile({ avatarUrl })` to persist it on the user. Never skip the second call — the uploaded file isn't reflected in `user_metadata` until you do.
- Display avatars with `expo-image`'s `<Image source={{ uri }} contentFit="cover" className="rounded-full ..." />`, not `react-native`'s `Image` — falls back to a `Ionicons name="person"` placeholder circle when there's no `avatar_url`.
- Requires a public Supabase Storage bucket named `avatars` to exist on the project (not created by app code) — check for it before assuming avatar upload works end-to-end on a fresh Supabase project.

## Confirm/Informative Modals (`src/components/ui/ConfirmModal.tsx`)
- `Alert.alert` is banned from this codebase entirely — every former call site (`toast.ts`, `InfoButton`, the Settings sign-out confirm) now renders through `<ConfirmModal>` so all dialogs share the app's design system instead of the native OS alert. Never add a new `Alert.alert` call; always use `ConfirmModal` (directly, for a one-off confirm dialog owned by a screen's local `useState`; or via `toast.ts`, for async-result notifications).
- Props: `visible`, `title`, `message?`, `confirmLabel?`/`cancelLabel?` (default to `t('common.done')`/`t('common.cancel')`), `variant?: 'default' | 'destructive'` (destructive renders the confirm button `bg-red-600 dark:bg-red-500` instead of `bg-primary dark:bg-primaryDark`), `onConfirm`, `onCancel?`.
- Omitting `onCancel` renders a single full-width confirm button (informative mode — the confirm button doubles as "close"). Passing it renders a two-button row (outline cancel + colored confirm). `InfoButton` (tooltip popover) and `ToastModalHost` (toasts) both use informative mode; the Settings sign-out confirm uses two-button destructive mode.
- For a screen-owned confirm dialog (e.g. a future "Delete Account"): own a `useState` boolean for `visible`, open it from the triggering `Pressable`'s `onPress`, and perform the actual async action inside `onConfirm` before closing. See `(tabs)/settings.tsx`'s sign-out flow for the reference usage.

## Notifications (`src/utils/notifications.ts`, `src/hooks/useSyncReminderNotifications.ts`)
- Reminders are **local, on-device notifications** via `expo-notifications` — not remote push. No push tokens are stored; nothing server-side schedules anything. This requires a real dev/EAS build (`eas build --profile development` or `npx expo run:ios`/`run:android`) since native modules don't work in Expo Go.
- `syncReminderNotifications(settings)` in `src/utils/notifications.ts` is the single entry point: it always cancels the two fixed-identifier notifications (`'morning-reminder'`, `'evening-reminder'`) first, then — if `settings.push_enabled` — reschedules both from `morning_time`/`evening_time` (`"HH:mm"` strings) via `Notifications.scheduleNotificationAsync` with `repeats: true`. Using fixed identifiers means re-syncing always replaces rather than duplicates, so it's safe to call on every settings change or app launch.
- `useSyncReminderNotifications()` wraps this in a `useEffect` keyed on `useReminderSettings()` and is called once from the root `src/app/_layout.tsx`, so reminders stay in sync app-wide, not just while Settings is open.
- Turning "Push notifications" on in `(tabs)/settings.tsx` calls `requestNotificationPermission()` first; if denied, the toggle reverts and `push_enabled` saves as `false` instead of silently scheduling notifications that will never show.
- `expo-notifications` is registered as an Expo config plugin in `app.json` alongside `@react-native-community/datetimepicker`.

## Haptics (`src/utils/haptics.ts`)
- **The only file allowed to import `expo-haptics`.** Everything else calls the semantic helper, so the same meaning always feels the same. The vocabulary:
  - `tick()` (selection): a value or option changed. Slider steps, chips, Yes/No, segmented controls, switches, tab switches, chart scrub, Wrap slides.
  - `tap()` (light impact): wizard page turns.
  - `press()` (medium impact): long-press opening an `ActionSheet`.
  - `success()`: an action actually finished.
  - `warning()`: a destructive `ConfirmModal` opens.
  - `error()`: an error toast.
  - `droplets()`: three soft impacts, 140ms apart. **Reserved for new check-ins.**
- **Vibrate on** a choice made, a value stepping, a completion or a warning. **Never** on scrolling, typing, plain navigation links, or every button press. Final Save buttons don't vibrate on tap; the success haptic fires only once the save resolves (via the success toast), so a failed save never feels successful.
- **Wizards use `useStepHaptic(step)`** (`src/hooks/useStepHaptic.ts`), one call per wizard, rather than a call per Next/Back button. It fires `tap()` whenever the step key changes (skipping first mount), so Next, Back, jump-to-step and summary "Edit" are all covered. `CheckinForm` keys it on `` `${step}-${flareUpStepDone}-${routineStepDone}` `` so its pre-steps count as pages. Add the hook to any new wizard.
- **Chosen spots:**
  - `PainSlider` ticks only when the integer changes: `onValueChange` can repeat the same value mid-drag, so it's guarded by a ref.
  - Segmented controls (History section/range, chart metric, Theme/Language switchers) tick only when switching to a *different* option.
  - Tabs tick via `screenListeners` in `(tabs)/_layout.tsx`, only when `!navigation.isFocused()`.
- **Check-in completion is two distinct moments, not a double buzz.** First, `success()` from the toast immediately on save. Then `droplets()` about 1.2s later from `WateringCelebrationHost`'s `WaterDrop`, timed to when the animated drop lands on the flower (`DROP_DURATION_MS * sqrt(0.8)`, because the drop reaches the flower at 80% of its quad-in eased travel). Edits don't get droplets, because the celebration only fires for *new* check-ins.
- **User setting:** "Vibration" `Switch` in Settings, backed by the persisted `useHapticsStore` (`enabled`, default `true`). Some chronic-pain users find vibration unpleasant. The helper reads it non-reactively (`getState()`, like `t()` reads the locale), so it works from Zustand actions and utils. Every call is fire-and-forget and swallows native errors.
- Haptics don't work in the iOS simulator. Verify on a real device.

## New-user journey (`src/lib/journey.ts`, `src/hooks/useJourney.ts`)
- **It replaced a spotlight/coach-mark tour**, which the user didn't like and which was deleted entirely. New users get **progressive unlocks** instead of every feature on day one.
  - **Milestones** count **logged days** (distinct `checkin_date`s, backfills included), not calendar time, so the reward is tied to showing up:
    - `history` at 3 days
    - `insights` and the `careStep` at 7
    - `reports` at 14
  - The logic is `getJourneyState()`, tested in `journey.test.ts`.
  - `useJourney()` reads `useCheckinHistory(365)`, the same cached key as History and Wrap. **While loading it reports everything unlocked**, so existing users never see locks flash on before their data arrives.

## Splash Screen (`src/components/AppSplashScreen.tsx`)
- Root `src/app/_layout.tsx` shows `<AppSplashScreen />` (not a bare `ActivityIndicator`) until `showSplash` clears — `showSplash = isLoading || profileLoading || todayLoading || !minTimeElapsed`, i.e. session load, the first `useProfile()`/`useTodayCheckins()` fetch, AND a 3-second minimum timer (`MIN_SPLASH_MS`) must all finish. Calling `useProfile()`/`useTodayCheckins()` directly in `RootLayoutNav` isn't just for the loading flag — since both hook to the same `['profile', user?.id]`/`['checkins', 'today', ...]` query keys `Home` uses later, this doubles as a prefetch: by the time the splash dismisses, Home's cache is already warm and shows no loading flash of its own.
- Two-stage splash handoff, per Expo's standard pattern: `SplashScreen.preventAutoHideAsync()` is called at module scope (top of `_layout.tsx`, outside any component) so the *native* splash (the static image from the `expo-splash-screen` config plugin) stays up; `SplashScreen.hideAsync()` is called in a mount-only `useEffect` in `RootLayoutNav`, right as `<AppSplashScreen />` starts rendering underneath — so the swap from native → custom JS splash has no blank-white gap. `app.json`'s plugin config `backgroundColor`/`dark.backgroundColor` are kept in sync with `theme.ts`'s `background`/`backgroundDark` for the same reason (avoid a color flash at handoff).
- `AppSplashScreen.tsx` renders the animation via `react-native-webview`, not `react-native-svg` — the source asset (`assets/icons/flowerJump.svg`) animates through embedded CSS `<style>`/`@keyframes`, which `react-native-svg` cannot execute (no CSS engine); a `WebView` runs a real browser engine so the keyframes play unmodified. The raw SVG markup is checked into `src/constants/flowerJumpSvg.ts` as a template-string constant (`FLOWER_JUMP_SVG`) rather than loaded as a Metro asset, to avoid needing a raw-text asset loader — regenerate that constant by hand if `assets/icons/flowerJump.svg` is replaced with a new animation.

## Success Animation (`src/components/ui/AnimatedCheckmark.tsx`)
- Reusable circle-draw + checkmark-draw success indicator, no Lottie — plain `react-native-svg` `<Circle>`/`<Path>` (added specifically for this; `react-native-reanimated`/`react-native-worklets` were already dependencies, unused until this) stroked with the strokeDasharray/strokeDashoffset "draw-on" trick, animated via Reanimated shared values (`useAnimatedProps`). Three chained stages, driven by `withTiming` completion callbacks (`withDelay(...withTiming(...))`), not a fixed total duration, so the sequence order is always correct regardless of frame rate: circle draws clockwise from 12 o'clock → checkmark draws inside it → the finished checkmark **holds** on screen for a beat (`holdDuration`, via a plain `setTimeout` since Reanimated has no delay-then-runOnJS primitive) before `onAnimationComplete` fires — without the hold, completion read as getting cut off right as it landed. All four durations live in `src/constants/animationConfig.ts` (`circleDuration`/`checkmarkDuration`/`checkmarkDelay`/`holdDuration`) rather than inline magic numbers.
- `strokeDasharray` on both the circle and the checkmark path is deliberately `` `${length} ${length * 2}` `` (gap much larger than dash), not a single value duplicated as dash=gap. At dash==gap, the hidden/visible boundary sits exactly at the path's start/end, and floating-point drift between the JS-computed length (`Math.hypot`) and the SVG engine's own rendered path length lets the round `strokeLinecap` leak a stray sub-pixel dot through right at the tip at animation start. The oversized gap gives that drift somewhere to hide.
- Optional `fillColor` prop renders a solid disc inside the ring (opacity fades in synced with the ring's own draw progress via `circleProgress`), with `checkmarkColor` auto-defaulting to white for contrast when a fill is set (override either explicitly). Omit `fillColor` for a plain outline ring (the original look, still used where the component already sits on a colored button).
- Exposes a `skip()` method via `forwardRef`/`useImperativeHandle` that jumps both shared values straight to 1, clears the pending hold timeout, and fires `onAnimationComplete` immediately — callers should never let this animation's total duration (~1.3s including the hold) block navigation for a user who moves on quickly. Full-screen overlay usages are tap-to-skip via the ref.
- Call sites: `ToastModalHost.tsx`'s `'success'` variant (small, 48px, outline, `colors.primary` — see the Toasts section) and Home's success overlay (large, 112px, `fillColor`/`color` both `colors.primary`, rendered via RN's `<Modal transparent>` — not a plain in-tree `View` — specifically so it covers the bottom tab bar, which is a sibling outside the screen's own view tree rendered by the `(tabs)` `Tabs` navigator; a plain `absolute inset-0` overlay stops above it). `CheckinForm.tsx`/`FlareUpForm.tsx`'s save buttons do **not** render this — they only ever show a plain `ActivityIndicator` while submitting, per explicit product decision: the checkmark on the button plus another one moments later in the success toast read as redundant/double animation, so the button stays a simple spinner and the toast is the one moment that gets the animated treatment. Generic enough to reuse for any future save/confirm moment (e.g. the physio visit log) — just mount a fresh instance per success event, don't try to reset/replay an existing one via prop changes.
- This still changed both `CheckinForm`'s and `FlareUpForm`'s `onSubmit` contract even without a button-level animation: neither performs navigation itself. Both return `Promise<{ error: string | null } | undefined>` (`undefined` means "intentionally short-circuited, e.g. a confirm dialog needs to be shown first — no error, no navigation") and a new `onSaved?: () => void` prop is called immediately after a successful save (not gated on any animation anymore — just after `setIsSubmitting(false)`). All call sites — `checkin/[type].tsx`, `checkin/backfill.tsx`, `checkin/edit/[id].tsx`, `flare-up/new.tsx`, `flare-up/edit/[id].tsx` — follow this split: `onSubmit` only runs the mutation and returns `{ error }`; `onSaved` does the toast + `router.back()` + celebration. Keep this split for any new screen that renders either form — it's still useful even without a button animation, since it keeps "did the save actually succeed" separate from "what happens after" (toast wording, whether to celebrate, navigation order). `flare-up/new.tsx` deliberately does **not** call `useCelebrationStore.getState().show()` even though `checkin/[type].tsx`/`checkin/backfill.tsx` do — the watering celebration is scoped to check-in streak completion (feeds the flower-health calculation), and logging a flare-up is a negative-health event, not an achievement; the success toast's own checkmark is the right amount of positive feedback there.
- **Onboarding's finish step does NOT play this animation inline.** Playing it on the onboarding screen and only then calling `router.replace('/(tabs)')` cut the animation off half-finished, visibly rendering mid-transition. Instead, `onboarding.tsx`'s `handleFinish` calls `useOnboardingCompleteStore.getState().markPending()` *before* saving (`src/store/useOnboardingCompleteStore.ts`, the same plain non-persisted Zustand pattern as `useCelebrationStore`), and calls `consume()` again if the save fails.
  - **`handleFinish` does not navigate at all.** The root layout's guard (`!needsOnboarding && inOnboarding` → `router.replace('/(tabs)')`) performs the single redirect once the refetched profile has `onboarding_completed`. It used to *also* call `router.replace('/(tabs)')` itself, which fired two overlapping fade transitions; that was the "something is off" finish. `isSaving` stays true on success so the button keeps spinning until the screen leaves.
  - Home waits `POST_TRANSITION_DELAY_MS` (450ms) after landing before presenting the checkmark's real `<Modal>`, so it never presents mid-fade (the documented Modal-vs-transition race).
  - Home reads `pending` directly off the store (no mirrored local state/`useEffect`+`setState` — that pattern trips the `react-hooks/set-state-in-effect` lint rule) and shows the same success `<Modal>` overlay once it lands, clearing the flag in its `closeCheckmark` handler so it only ever plays once.

## Navigation Transitions (`src/app/_layout.tsx`)
- The root `<Stack>`'s `screenOptions.animation` defaults to `'slide_from_right'` — explicit, not native-stack's implicit `'default'`, because Android's implicit default can render as an inconsistent fade/scale depending on OS/RN Screens version; naming it pins the same directional slide on both platforms. Plain-push screens (most of the tree) inherit this and need no per-screen override.
- `(tabs)`, `onboarding`, `(auth)` each override to `animation: 'fade'` — these are reached via `router.replace(...)` (auth/onboarding/tabs mode switches), not a user-initiated push, so a directional slide would misread as "entering a sub-page."
- Every `presentation: 'modal'` screen also sets `animation: 'slide_from_bottom'` explicitly, alongside `presentation: 'modal'` — the presentation option controls container/dismiss-gesture semantics, not the entrance animation, and leaving `animation` unset lets Android fall back to a platform default not guaranteed to match iOS's implicit slide-up.
- Avoid `'ios'`/`'ios_from_right'` for any of this — both are iOS-only values (no-op on Android), defeating the cross-platform-parity point of setting `animation` explicitly at all.
- This does not change the `ToastModalHost`/`WateringCelebrationHost` real-`<Modal>`-dismiss race documented in the Toasts section above — both hosts already avoid RN's real `<Modal>` for exactly that reason, so naming an already-implicit dismiss animation explicitly doesn't introduce a second native window or otherwise touch that risk.

## Pain/Neck Tracker Domain
- Supabase tables (created directly in the dashboard, no local `supabase/` CLI folder): `checkins` (unique on `user_id, checkin_date, type`; shared pain/stiffness/range_of_motion fields plus morning-only and evening-only columns, `symptoms jsonb`, `triggers text[]`), `flare_ups`, `reminder_settings` (PK `user_id`), `profiles` (PK = auth user id, auto-created via `on_auth_user_created` trigger), `physio_assessments` + `muscle_findings`, `routines` + `exercise_logs` (see below). RLS scopes every table to `auth.uid()`. Hand-written types matching this schema live in `src/types/database.types.ts` — there's no `supabase gen types` output, so keep these in sync manually if the schema changes.
- **`routines` + `exercise_logs`** (`supabase_routines_migration.sql`, repo root — run once in the Supabase SQL editor, same manual-migration convention as `supabase_onboarding_migration.sql`): a `routine` is a set of prescribed exercises (`exercises jsonb`, array of `{ id, name, muscle_group, target_sets_reps, instructions, caution_notes }` — `id` is client-generated, not a DB row id, since exercises don't have their own table), optionally linked to the `physio_assessments` visit it was generated from via `physio_visit_id` (nullable — null when created from free text/onboarding instead). **Any number of routines can be `in_rotation = true` per user at once** — see `supabase_routines_migration_v2.sql` below; this replaced an earlier single-active model. `exercise_logs` records one adherence check-in per `routine` (`status: 'FULL' | 'PARTIAL' | 'SKIPPED'`, DB `check` constraint), with per-exercise outcomes in `completed_exercises jsonb` (array of `{ exercise_id, completed, pain_discomfort_level (0-10, app-enforced only, same as every other 0-10 field in this schema), flagged_pain, note }` — `exercise_id` matches a `RoutineExercise.id` from the routine it's for). `Routine`/`RoutineInsert`/`RoutineExercise`, `ExerciseLog`/`ExerciseLogInsert`/`CompletedExercise`/`ExerciseLogStatus` types live in `database.types.ts`. Hooks: `useRoutinesInRotation()` (`src/hooks/useRoutines.ts`, `in_rotation = true` list query, ordered oldest-first — read-only, routines are only ever created via the `generate-routine` edge function, no manual-create UI) and `useTodayExerciseLog`/`useCreateExerciseLog`/`useAppendExerciseLogNote` (`src/hooks/useExerciseLogs.ts`, same never-throw `{ error }` pattern as `usePhysioAssessments.ts`). `useTodayExerciseLog` finds "today's" log by fetching the last 5 rows for the routine and filtering client-side with `isToday()` (`src/lib/dates.ts`) rather than a `logged_at` date-range query — `logged_at` is a `timestamptz`, so a UTC range query risks the same midnight-boundary bug `todayLocalDate()` was written to avoid.

This broke a real physio pattern: alternating between routines prescribed for different days (e.g. Routine #1 one day, Routine #2 the next). The migration renames `is_active` → `in_rotation` and drops the trigger entirely; rotation membership is now just a plain boolean the app sets directly, with **no automatic deactivation side effects**. `useCreateRoutine()` now sets `in_rotation: true` on generate (joins the rotation, doesn't replace anything); a new `useSetRoutineRotation()` mutation is the only way membership changes afterward, exposed via `routine/view.tsx`'s long-press menu ("Add to rotation" / "Remove from rotation" — reversible and non-destructive, so no `ConfirmModal`, unlike Delete). **By design, the user manually picks which routine to train each day** — there's no automatic day-of-week assignment or alternation logic; this keeps the model simple and matches how physios actually phrase it ("alternate as it suits you").

- **`generate-routine`** (`supabase/functions/generate-routine/`) is the AI generator for `routines`: given `{ source: 'physio_visit', physio_visit_id }` or `{ source: 'manual_input', input_text }`, it builds a prompt from `profiles.injury_description` (diagnosis context, same as `analyze-patterns`/`physio-summary`) plus either a fetched `physio_assessments` row's `overall_notes`/`muscle_findings`, or the raw `input_text`, asks Claude for a JSON routine, validates the shape (every exercise object has all 6 required string fields — `isValidRoutinePayload`/`isValidExercise`), and only then inserts into `routines` with `in_rotation: true` (joining the rotation — no other routine is affected). Deliberately does **not** trust a client-supplied `user_id` even though earlier specs listed one as an input — `user.id` always comes from the authenticated session (`supabase.auth.getUser()`), matching how every other write in this schema is scoped; accepting a body-supplied id would let any authenticated caller write into another user's account. Response is `{ routine, summary }` — `summary` is returned for the caller to show (e.g. a toast/description) but is **not** persisted anywhere, since `routines` has no summary column.

  - **Carry-forward exercises**: the request body also accepts `carry_forward_exercises?: RoutineExercise[]` — exercises from the user's *current* routine to keep verbatim in the new one, since most of a routine typically repeats visit to visit and re-describing unchanged exercises by hand was pure friction. The edge function validates each with the same `isValidExercise()` used for Claude's own output (this input is client-supplied, unlike everything else in the request) and prepends the valid ones to Claude's newly generated exercises — **spliced in as-is, never re-run through Claude**, since asking an LLM to "reproduce unchanged" risks subtle rewording of text that's already known-good.
    - **Real bug this caused**: carried-forward exercises keep whatever `id` they had in the *previous* routine (e.g. `"ex_1"`), and Claude always starts its own numbering at `"ex_1"` too (per the prompt's own example) — so combining the two verbatim reliably produced duplicate ids (React's "Encountered two children with the same key" on the review/exercise-list screens) any time carry-forward was used alongside newly generated exercises. - **Monthly Wrap** (Spotify-Wrapped-style story recap of the previous calendar month). By explicit decision it is **monthly only**: a weekly one was rejected because it would stop feeling special and a week is too little data. It also has **no share/export in v1**, so there's no `react-native-view-shot`/`expo-sharing` dependency; add those only if sharing is requested.
  - **Tone rule:** pain data is mostly negative, so the Wrap celebrates showing up and progress. There is **never a "worst day" slide**; `calmestWeek` is its positive counterpart. "Worse" outcomes (pain up, more flare-ups) use compassionate copy and calm backgrounds, never red.
  - The engine is `src/lib/wrap.ts` (`buildMonthlyWrap`, pure, tested in `wrap.test.ts`): a `WrapSlide` discriminated union where each slide generator returns `null` when the data doesn't support it. All numbers are plain client-side arithmetic, with no AI call, reusing `dailyAverages`/`meanOfDays`/`countPainFreeDays` from `painTrend.ts`. Thresholds:
    - a month needs ≥7 logged days to get a Wrap at all (`isWrapAvailable` is the cheap check)
    - month-over-month comparisons need ≥3 days in both months; a change under 0.3 counts as "steady"
    - `calmestWeek` needs ≥2 Mon–Sun weeks with ≥3 days each
    - `sleep` needs ≥3 mornings on each side of 7h and a pain gap of ≥0.5 in favor of more sleep
    - `training` names the top exercise by *name*, not id, since ids are only unique per routine
    - range of motion's tone is inverted, because higher is better
    - flare-ups and exercise logs are bucketed by `toLocalDate()`
  - `useMonthlyWrap(month)`/`useAvailableWraps()` (`src/hooks/useMonthlyWrap.ts`) reuse the 365-day `useCheckinHistory`/`useFlareUps` caches the History tab already holds. "Seen" state is a persisted per-device Zustand store, `useWrapStore` (`seenMonths`), not a DB column, because it only controls whether Home's `WrapReadyCard` still shows (last month's Wrap, until opened once). Past Wraps stay reachable from the "Monthly Wraps" chip row on History's overview.
  - The story screen is `src/app/wrap/[month].tsx`, registered with `presentation: 'fullScreenModal', animation: 'fade'` (an immersive takeover, not a sheet). `StoryProgress` segments fill via a shared value over 6s and auto-advance, except on the last slide. Tap the left third to go back and the rest to go forward, hold to pause, and a haptic fires on each slide change. It drives the shared value with `progress.set()`/`.get()`, **not** `progress.value = …`, because the React Compiler lint rule (`react-hooks/immutability`) errors on mutating a value passed into a hook. Use `.set()` for any new imperative shared-value writes in component callbacks.
  - All slide copy and visuals live in one `slideContent()` mapper in `src/components/wrap/WrapSlideView.tsx`, with backgrounds in `SLIDE_STYLES` (`lightText` drives native-prop colors like the close icon). Month names: `'LLLL'` (standalone, "spalis") inside sentences like "Jūsų {{month}}", and `'MMMM'` (genitive, "spalio") for "Jūsų {{month}} apžvalga". date-fns' `lt` locale distinguishes the two, and the wrong one is ungrammatical.

- **Check-ins require one real answer per wizard step. That silently inflated the pain-free tile, the graph and Monthly Wraps. The rules live in a pure helper, `src/lib/checkinCompleteness.ts` (`getStepIssue`/`firstIncompleteStep`, tested):

  - **Step 2:** at least one answer. Morning: sleep quality, sleep hours or sleep position. Evening: activity, screen time, `did_exercises`, or a non-blank note.

  - Pre-steps (flare-up follow-up, routine training) stay skippable.

The value stays `null` until touched. A tap or release with no movement still commits 5, via `onSlidingComplete`, because `onValueChange` doesn't fire when the value doesn't change. **Never put 5 in the form defaults for these**, or untouched check-ins would save as 5 and flatten the stiffness and mobility graph and Wraps. The middle labels are descriptive rather than "Neutral", because a 5 on these scales is a moderate amount, not neutral. The old unused `checkin.moderate` ("Neutral") key was removed. - **`PainTrendChart` (History tab) buckets its data and must never unmount on a range switch.** `history.tsx` no longer runs a per-range `useCheckinHistory(rangeDays)`/`useFlareUps(rangeDays)` query: each range had its own query key, so switching briefly returned `[]`, which blanked the stat tiles and made the chart `return null` (the flicker). It filters the existing 365-day calendar fetch client-side with `rangeStartDate()` instead, and passes the chart the full `allCheckins` plus `range: 'week' | 'month' | 'all'`. Bucketing lives in `src/lib/painTrend.ts` (`buildTrend`, pure, `today` injected, tested in `painTrend.test.ts`): Week = 7 daily points with dots, Month = 30 daily points with only the latest point highlighted, All = starts at the first check-in and picks day/week (Monday-start)/month buckets by span (≤45d / ≤180d / longer) to stay at roughly ≤30 points. Every bucket is a mean of *daily* averages (`dailyAverages`, also used for the avg-pain tile). Empty buckets are `null`, `x` is the bucket index across the full range, and the chart uses `connectMissingData`. The readout is in the **card header** (large value top-right with `/10`, plus `avg` for week/month buckets; the date replaces the subtitle) rather than near the touch point, because the thumb covers everything at or below where it presses. Empty buckets show `—` / "No check-in" and no dot. Readout dates come from `formatBucketDate()` in `painTrend.ts`.
  - **Metric switcher** (Pain / Stiffness / Mobility chips inside the card, local non-persisted `useState`, always opens on Pain): one chart for all three 0–10 body metrics instead of a chart per field. That was a deliberate product call: users enter a lot of data, but separate charts per field would just be a wall nobody reads. `buildTrend(..., metric)` / `dailyAverages(..., metric)` **skip `null` values** (`stiffness_level`/`range_of_motion` are nullable), and bucket boundaries depend only on range and check-in dates, never on the metric. ## Internationalization (i18n)
- No i18n library (`i18next`, `expo-localization`, etc.) — a small custom solution mirroring the `useThemeStore` pattern, since this is a two-language (English/Lithuanian), no-plural-rules app that doesn't need a full library.
- `src/store/useLocaleStore.ts` — persisted Zustand store (`persist` + `createJSONStorage(() => AsyncStorage)`, same shape as `useThemeStore`): `locale: 'en' | 'lt'`, `setLocale(locale)`. Defaults to `'en'`.
- Dictionaries live in `src/lib/i18n/translations/en.ts` and `lt.ts`, one deeply-nested object per file grouped by domain/screen (`common`, `auth`, `home`, `checkin`, `flareUp`, `history`, `detail`, `patterns`, `settings`, `editProfile`, `tabs`, `screenTitles`, etc). `lt.ts` is typed `export const lt: typeof en = {...}` — TypeScript fails the build if `lt` is missing a key `en` has (or vice versa), so that's the enforcement mechanism, not a runtime check.
- `src/lib/i18n/useTranslation.ts` exports:
  - `useTranslation()` — the hook for use inside components: `const { t, locale } = useTranslation()`, subscribed to `useLocaleStore` so it re-renders on language change.
  - `t(path, vars?)` — a **non-reactive** plain-function twin for contexts that can't call hooks (Zustand store actions like `useAuthStore.uploadAvatar`, plain utils like `utils/image.ts`, and TanStack Query `mutationFn`/`queryFn` closures). It reads `useLocaleStore.getState().locale` directly instead of subscribing — fine for one-shot lookups in a callback, not for anything that needs to re-render on locale change.
- Calling convention: `t('domain.key', { var: value })`, with `{{var}}` placeholders in the dictionary string interpolated via simple `.replace()` — no plural rules, no ICU. E.g. `t('home.daysSinceInjury', { days })` → `'{{days}} days since injury'`.
- Every user-facing string (JSX text, `Alert.alert`/`toast.*` args, `placeholder`, `accessibilityLabel`, `InfoButton` title/message) must go through `t()` — never hardcoded. New keys are added to **both** `en.ts` and `lt.ts` in the same change; TypeScript's structural check on `lt: typeof en` is what catches a forgotten language.
- Zod schemas (`src/lib/validations/*.ts`) are built at module load time, before any component can call `useTranslation()`, so their `.min()`/`.email()`/`.refine()` messages are stable i18n key strings (e.g. `'validation.emailRequired'`) rather than literal English. Screens run the resolved message through `t()` at the point they read it: `error={errors.email?.message && t(errors.email.message)}`. Only the auth forms (`login.tsx`, `register.tsx`, `forgot-password.tsx`, `modal/edit-profile.tsx`) currently render field errors this way — `checkin.ts`/`flareUp.ts` schema messages exist as keys but aren't surfaced to any UI yet (those forms don't read `formState.errors`), so wire them the same way if that changes.
- `LanguageSwitcher` (`src/components/ui/LanguageSwitcher.tsx`) mirrors `ThemeSwitcher` exactly (segmented control) and lives in its own "Language" section in `(tabs)/settings.tsx`, right after Appearance.
- `ErrorBoundary` is a class component and can't call hooks directly — its fallback UI is a separate functional component (`ErrorFallback`) that calls `useTranslation()`, rendered from `ErrorBoundary.render()`.
